## Hypothesis
After e004 the three backward kernels are 3.49 ms of a 9.9 ms forward + backward on trained inputs and 1.34 s of the
7.76 s trained step (17 %). They work at the saved final lambda, where 35 % of the (64-row block, 32-key tile) pairs
hold any key of any row's support (e004: 0.345 of the flags live at exit on FineWeb, 0.296 on ArXiv 16k). A dead tile
has r = w = 0 on every row, so it adds exact zeros to delta's numerator and denominator, to dQ, dK and dV: skipping it
changes no bit, provided no tile with a live entry is skipped. The forward already owns the flags; its output sweep can
leave them valid at the final lambda (a processed tile is re-flagged from the final lambda with the 2 mu margin, a
skipped tile was trusted and is outside the window by >= mu). The backward reads lambda from the same saved tensor, so
there is no trust test to make. The forward paid ~70 % of the tile-count saving (e004); the same efficiency here gives
3.49 -> ~2.0 ms. dK/dV loses a little more: its query blocks start at the key tile's offset, which is not a multiple of
64 for odd tiles, so a block straddles two forward blocks and is skipped only if both flags are dead.

## Change
- `stieltjes/triton_stieltjes.py`: `_fwd_kernel` constexpr `FLAGS_OUT` (= SKIP and `SKIP_BWD`): the output sweep
  rewrites the flag of every tile it processes from the final lambda (same `dthr2` test as the Newton sweeps). The three
  backward kernels take `Live, NB, NT` and a constexpr `SKIP`: delta and dQ test `Live[block, tile]` per key tile; dK/dV
  (fixed key tile, loop over query blocks that start at the tile's offset) tests the flags of the one or two forward
  blocks its 64 rows lie in. `StieltjesAttention.forward` keeps the flags on `ctx.live` (196 KB at the training shape);
  dense map, num_iter 0 or `SKIP_BWD = False` give `SKIP` off, which is the e004 backward. Module switch `SKIP_BWD`
  (False = the e004 kernel, forward included). `model.py`, the frozen baseline: untouched.
- Known difference, same kind as e004's forward: a skipped tile no longer turns a non-finite dO or V into NaN for rows
  that give that tile zero weight (0 x inf). Every row has a live tile, so a non-finite input still reaches every row's
  dQ and the live keys' dK/dV; a diverged run still shows NaN gradients. Not exercised by the gate (finite inputs).
- `bench_kernel.py`: `real` adds forward + backward through autograd (baseline, `SKIP_BWD` off, on; ms and dq, dk, dv
  identity); `skipcheck` adds dq, dk, dv against the e004 backward and the baseline on all 480 cases; `micro` passes
  the flags to the per-kernel backward launches and adds a `nobskip` row; `wrap --kernel=cand_nobskip`.
- `osc/kernel_time.sbatch` `PLAN=ab_trained`: comparator selectable with `CMP=` (`cand_nobskip` here).

## Interpretation
Backward tile skipping is kept: exact (dq, dk, dv bit-identical on every case of the gate) and 9.8 % off the trained
step, 7.0 % off the step at initialisation. The kernel-level and step-level numbers agree: (9.88 - 7.79) ms x 384 calls =
0.80 s against 0.76 s measured. The primary metric is now 7.82 s/step at step 0 falling to 6.96 s/step at the end of
training, against 13.69 for the frozen baseline (-43 % to -49 %), 9.88 for ASEntmax and 6.26 for softmax; the trained
Stieltjes step is within 11 % of softmax's. As in e004, where a whole run averages between the two ends is not measured.
The backward keeps more of the tile-count saving than the forward does (52 % saved at 65 % of the tiles dead, against
37 % for the forward): its tiles are heavier (two or three `tl.dot` per tile), so the per-tile flag test is a smaller
fraction of what is skipped.
Where the trained 6.96 s goes by the kernel-level numbers: forward 6.11 ms x 384 = 2.35 s (34 %), backward 1.67 ms x 384
= 0.64 s (9 %), everything else 3.97 s (57 %). e001's synchronised timers put everything that is not attention at
3.24 s, so either the kernels cost ~0.7 s more inside the step than in the microbench, or the non-attention part is
larger than e001's timers said; this record cannot tell which (no timed step was run on the candidate).
What is left in the kernels is the forward's Newton loop: 15 sweeps of which 14 run at ~37 % of the tiles.

so once every row of a block repeats (lambda_t equal to lambda_{t-1} or lambda_{t-2}) the remaining sweeps only
alternate between two known values and the block can stop and take the one sweep 15 would have ended on. e003 closed
early exit for the test "the update is exactly zero" (14 % of blocks); the 2-cycle test is the same idea with one more
value of history. How many sweeps it saves on trained inputs is unknown and is measured in the same record.
