## Hypothesis
The forward kernel is slow because `tl.static_range(NUM_ITER)` unrolls 15 copies of the Newton sweep into one kernel:
e001 measured a cost per sweep that grows with NUM_ITER (0.5 / 1.3 / 2.0 ms at NUM_ITER 5 / 15 / 30 after removing the
~1 ms launch overhead), where one sweep of this size should cost what the it=0 kernel pays (0.25 ms for row-max +
output). Emitting the loop once (`tl.range`, an `scf.for` in Triton 3.1.0 `code_generator.visit_For`) removes whatever
scales with the copy count (shared memory per block, registers, code size: not yet identified) and makes the forward
affine in NUM_ITER with the same arithmetic in the same order, so outputs and gradients are unchanged.

## Interpretation
The unrolled Newton loop was the cost: with one copy of the sweep body the forward is affine in NUM_ITER at
0.52-0.61 ms per sweep, the forward kernel is 2.27x faster, and the 125M step of all three Stieltjes rows drops by
34-35 % to 8.9-9.2 s, below ASEntmax (9.88 s) and 2.65 s above softmax (6.26 s). The arithmetic is untouched (bit
identity on 110 cases and both e2e evals), so this is a pure code-generation fix and applies to every existing
checkpoint and to the 350M runs (48 GPU-h per Stieltjes run at the old kernel; the same ratio would make it ~31).
The mechanism is identified only as far as "scales with code size, not shared memory or warps" (instruction-cache
pressure or register allocation across the copies are both consistent); it was not separated further because the fix
does not depend on it.
Where the 8.91 s now goes, by arithmetic from this job's micro and e001's timers (not re-timed in the step):
forward 384 x 10.0-10.6 ms = 3.8-4.1 s (43-46 %), backward 384 x 3.5-3.7 ms = 1.3-1.4 s (15-16 %), everything that is
not attention 3.2 s (36 %). One Newton sweep at 0.59 ms covers 96 x 2048 x 2048 / 2 scores, about 44 TFLOP/s of
tensor-core work against a 312 TFLOP/s A100 peak, so the sweep is not at the dot-product bound either.
Not shown: whether 64x32 tiles and the default launch parameters are still the best choice (they were tuned on the
unrolled kernel), and how much of each sweep is spent on tiles outside every row's support.
