## Hypothesis
After e005 the forward kernel is 6.11 ms of a 7.79 ms forward + backward on trained inputs (2.35 s of the 6.96 s trained
step, 34 %), and most of it is the Newton loop: 15 sweeps, 14 of them at ~37 % of the tiles. e003 closed early exit for
the test "the Newton update is exactly zero on every row" (14 % of blocks settle; lambda is still changing at sweep 15
in 86 %). But lambda still changing does not mean it is still converging: the per-sweep live-tile fraction stops moving
at sweep 5 (FineWeb) to 8 (ArXiv), which looks like convergence followed by rounding jitter. The Newton update is a
deterministic function of a row's lambda alone, bit for bit (a skipped tile adds exact zeros, e004), so jitter is a
cycle: once lambda_t == lambda_{t-2} on a row, the sweeps still to run alternate between lambda_t and lambda_{t-1}. A
block whose rows all repeat with period 1 or 2 can therefore stop and take the value the 15th sweep would have ended on
(lambda_t if an even number of sweeps remains, lambda_{t-1} if odd; the same value on a fixed-point row). That is
bit-identical by construction, with no tolerance and no change to num_iter: the kernel returns exactly the lambda that
15 sweeps return. Rows on longer cycles keep their block sweeping to the end. The speed depends on the sweep at which
the slowest row of each block starts to repeat, which is not known for trained inputs and is measured in this record.

Desktop evidence before the prediction (random inputs, triton 3.6, lambda_t read from kernels launched at NUM_ITER =
1..15; not the A100 and not trained logits): at (2, 12, 2048, 64), q3/d2, exp slopes, 64-row blocks, the period <= 2
test lets 98.4-100 % of the blocks leave early and saves 8.9-9.8 of 15 sweeps; the fixed-point test alone (e003's) lets
40-83 % leave and saves 3.7-8.2; allowing periods 3 and 4 as well adds under 1 point. Period-3 rows exist (3 rows of
~3,400 in the first failing skipcheck cases, all in the first three positions of a sequence, where the support is 1-3
keys); they keep their block in the loop, which is correct.

## Change
- `stieltjes/triton_stieltjes.py` `_fwd_kernel`: constexpr `CYC` (module switch `EXIT_CYCLE`, on for num_iter > 1; off
  = the e005 kernel). The sweep body sits under `if active:`; after each sweep
  `cyc = all rows (lam_new == lam | lam_new == lam_p1 | padding)`, then `lam_p1 = lam`,
  `lam = where(cyc and odd number of sweeps left, lam, lam_new)`, `active = not cyc`. Two [BLOCK_M] vectors of history,
  one compare-and-reduce per sweep; an inactive sweep is one branch. Applies to the dense map too (same argument). The
  tile flags stay valid: the output sweep tests `trust` against the running maximum as before, and the flags written by
  the last sweep that ran were computed at a lambda the running maximum covers. Backward kernels, `model.py`, the frozen
  baseline: untouched.
- Toolchain finding while testing this on the desktop (triton 3.6): the first draft initialised the history with
  `lam_p1 = lam`, an alias, and re-bound it in the loop with `lam_p1 = lam`. Triton 3.6 does not carry such a name
  through the loop: it keeps its initial value, so the test compared against lambda_0 and fired on a period-3 row
  (18 of 352 quick skipcheck cases differed in lambda on 1-2 rows, O and S identical). Minimal reproduction in
  `bench_kernel.py aliascheck`. The fix is `lam_p1 = lam + 0.0` (a value of its own); 352 of 352 after it. The same
  check shows the e004 / e005 pattern `lam_hw = lam` followed by `lam_hw = tl.maximum(lam_hw, lam)` IS carried on 3.6
  (the running maximum behind `trust`), and reading `visit_For` of the installed 3.1.0 on Ascend says both patterns are
  carried there (loop-carried names are collected by name, each gets its own block argument); `aliascheck` now runs
  first in both job scripts so the A100's 3.1.0 answers by measurement, not by my reading. If `lam_hw` were not carried
  on 3.1.0 the e004 / e005 kernels would still have passed every test (no tested input needs the guard), so this is
  the first direct check of that guard on the toolchain of record.

## Interpretation
The exact cycle exit is kept: 11.7 % off the trained step and 10.4 % off the step at initialisation, with every
output and gradient bit unchanged. The kernel-level and step-level numbers agree: (7.89 - 5.91) ms x 384 calls = 0.76 s
against 0.82 s measured. The primary metric is now 7.01 s/step at step 0 falling to 6.15 s/step at the end of training,
against 13.69 for the frozen baseline (-49 % to -55 %), 9.88 for ASEntmax and 6.26 for softmax: the trained Stieltjes
step is level with softmax's (1.8 % under it, but the softmax number is from e001's job on another node, so "level" is
all this supports). At the kernel level the reason is visible: forward + backward on trained inputs is 5.91 ms, under
SDPA softmax + bias at the same shape (7.24 ms), because 65 % of the tiles are never touched. Where a whole run averages
between the two ends is still not measured.
e003's "early exit closed" was a statement about the fixed-point test only: lambda was still changing at sweep 15 in
86 % of the blocks, but 91 % of the blocks had been in a 2-cycle of rounding jitter since sweep ~8.
Where the trained 6.15 s goes by the kernel-level numbers: forward 4.24 ms x 384 = 1.63 s (26 %), backward 1.67 ms x 384
= 0.64 s (10 %), everything else 3.88 s (63 %). The same subtraction for softmax (7.24 ms at B=8, i.e. 2.78 s per step)
leaves 3.5 s, so the Stieltjes row carries ~0.4 s outside its kernels that softmax does not: the copies at the call
site (three `.contiguous()` in, one out, dO and the three gradients on the way back) and the mb 8 x 32 schedule.
Inside the forward what remains is 1 row-max sweep over every tile, ~8 Newton sweeps at ~40 % of the tiles and the
output sweep; the next exact step there (flagging tiles from the row-max sweep so the first Newton sweep skips too) is
worth at most ~0.3 ms of 4.24.
