## Hypothesis
After e006 the kernels are 5.91 ms of forward + backward per call on trained inputs (2.27 s of the 6.15 s trained step);
what is left of the Stieltjes row's own cost outside them is the call site. `model.py:_stieltjes_fused` copies q, k and
v (transposed views of one c_attn output) to contiguous (B, H, N, D) tensors before every call, the kernel writes O in
(B, H, N, D) order and the model copies it back with `transpose(1, 2).contiguous()`, and the backward copies dO and
returns dQ, dK, dV in (B, H, N, D) order, which autograd's `view` backward has to reshape (copy) before the split's
backward concatenates them: eight 25 MB copies per call, 384 calls per step. The kernels already take every tensor's
strides (the baseline was written for "fused-qkv transpose views", see the comment at `off_z`), so none of the copies
is needed: the kernels can read the views and write their outputs in the views' memory order. The values cannot change
(the same loads and stores at other addresses), so this is bit-identical by construction.
What it is worth is not known: e001's synchronised in-step timers put the forward call site outside the kernel at
0.25 ms per call (0.10 s per step), the micro in e006 puts the three input copies at 0.81 ms (5.31 against 4.50 ms) and
copies in forward + backward at 1.10 ms without counting the O and dO copies. That brackets the copies at 0.6-1.6 ms
per call, 0.2-0.6 s per step (4-10 % of 6.15 s). Counter-argument: strided loads may be slower than contiguous ones
(a 64-row q tile becomes 64 segments of 128 bytes 4.6 kB apart instead of one 8 kB run, and the Newton loop reloads
every live k tile 8 times), which would give some or all of it back; the micro row "forward kernel on views" measures
exactly that.

## Interpretation
The copies around the kernels are not where the step time is. Removing eight 25 MB copies per call changes the trained
step by 0.000 +- 0.007 s (0.0 %), the step from scratch by -0.1 % and the AS row by -0.2 %, all inside the step-to-step
spread. Two reasons, both measured: the copies are cheap on the GPU (0.19 ms per forward call in the micro), and the
kernel pays for strided inputs (+0.69 ms on the forward kernel alone), so the micro's net -0.37 ms per call (0.14 s per
step expected) does not survive in the step. I priced the copies from the difference of two micro rows (5.31 against
4.50 ms) that contained the strided-load penalty, not copy time: the hypothesis' counter-argument was the right one.
Decision: **reverted, not kept**. `stieltjes/triton_stieltjes.py` and `model.py` are back at 9a9e809 (the e006 kernel
and call site) byte for byte; `viewcheck` and `cand_copy` are removed from the harness. The only measurable effect was
-0.56 GB of peak allocation on the AS row, not worth a `model.py` change and a strided kernel.
What the timed step adds: (1) the call site outside the autograd Function is 0.05 ms per call, so nothing is left there;
(2) the forward Function takes 6.22 ms in the synchronised step against 4.24 ms (contiguous) / ~4.9 ms (strided, by the
micro's penalty) for the same kernel on captured q/k, the same +1.3 ms excess as e001 (24.1 against 22.8 ms). Part of
it is CPU time inside the wrapper: `_pick_blocks` asks the driver for the device's shared memory on every forward,
1.01 ms per call (micro, 0.39 s per step if none of it overlaps GPU work). Whether that CPU time is hidden behind
queued GPU work in the unsynchronised step is not known: the timers cost 0.69 s per step, which says CPU and GPU work
normally overlap, but the Stieltjes row also carries ~0.7 s outside its kernels that the softmax row does not (e006),
and e007 has now shown that it is not the copies.
