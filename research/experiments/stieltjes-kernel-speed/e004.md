## Hypothesis
On a trained model most of the forward's tile work is spent on (64-row block, 32-key tile) pairs in which no row has a
key inside the window: e003 measured 47 % of the swept tiles live at the first Newton sweep and 35 % at the end (FineWeb
N=2048, 12-layer mean), which is 7.5 of 17 sweeps of tile work if a mask is carried from sweep to sweep. A dead tile adds
exact zeros to f, f', S and O, so skipping it changes no bit, provided the kernel never skips a tile that has a live
entry. e003 could only observe that dead tiles stay dead (lambda decreases by rounding on 9 % of rows), so the kernel
does not rely on it: a tile is flagged dead only if every row is outside the window by a margin 2 mu (mu = 1e-3 d), and
a block trusts its flags in a sweep only while no row's lambda is more than mu below its running maximum; otherwise it
sweeps every tile. The remaining mu covers rounding and FMA differences between the flag test and the weight test
(triton 3.1.0 compiles with `enable_fp_fusion=True`, read in `backends/nvidia/compiler.py`). So the output is bit
identical to the e002 kernel by construction and the speed depends on how sparse the heads are.

## Change
- `stieltjes/triton_stieltjes.py` `_fwd_kernel`: constexpr `SKIP` (on for the windowed map with num_iter > 0, off for
  dense, where the code path is the e002 one), a uint8 flag per (batch x head, query block, key tile) in a scratch
  tensor `Live` (ones at launch; 196 KB at the training shape, 1.5 MB at 16k), runtime args `dthr2 = d (1 + 2e-3)` and
  `mu = 1e-3 d`. Newton sweeps and the output sweep: `go = flag != 0 or not trust`; a processed tile in a Newton sweep
  rewrites its flag from `lambda - max_j s_ij < dthr2` over the valid rows. `trust` = every valid row has
  `lambda_hw - lambda <= mu` (false for NaN / inf, so those propagate as before). The first Newton sweep sweeps every
  tile. Module switches `SKIP_TILES` (False = the e002 kernel) and `SKIP_MU_REL` (negative = never trust, the fallback
  path), `_forward(..., return_live=True)` for the bench. Backward kernels, `model.py`, the frozen baseline: untouched.
- `bench_kernel.py`: `real` (forward on captured q/k: baseline, no-skip, skip; ms, identity, flag fraction),
  `skipcheck` (flags trusted / never trusted / logits of 2e4 where one ulp of lambda exceeds mu, each bit for bit
  against no-skip and the baseline, 480 cases), `wrap --kernel=cand_noskip`, a no-skip row in `micro`; `summary`
  drops the first three logged steps by position (resumed runs start at iter ~4770).
- `osc/kernel_time.sbatch` `PLAN=ab_trained`: micro, real, then no-skip against skip for 20 steps each on
  `wstieltjes_q3_d2_xs` and `aswstieltjes_q3_d2_zi_xs` resumed from copies of the trained checkpoints (unmodified
  `train.py --init_from=resume`), and on `wstieltjes_q3_d2_xs` from scratch. `osc/kernel_gate.sbatch`: + `skipcheck`.

state); where in between the average sits is not measured here.

## Interpretation
Tile skipping is kept: exact (bit-identical outputs, lambda, S and gradients on every case in the gate) and 13 % off the
step of a trained model, 5 % off the step at initialisation. A training run sits between those two ends; where its
average lies was not measured (it depends on how fast the heads sharpen), so the honest statement of the primary metric
is 8.44 s/step at step 0 falling to 7.76 s/step at the end of training, against 13.69 for the frozen baseline (-38 % to
-43 %), 9.88 for ASEntmax and 6.26 for softmax. Both pre-profile predictions given to the user are now met (>= 20 % with
the gate passed; below ASEntmax's 10.0 s/step).
The skip is not free. Free skipping at the measured tile counts would be 10.18 x 7.49 / 17 = 4.5 ms; the kernel does
6.42. With e003's +8 % per processed tile for the lost pipelining, a skipped tile still costs about a quarter of a
processed one (flag load, branch, the loop bookkeeping), so the saving is ~70 % of the tile-count saving.
Where the trained step's 7.76 s now goes: forward kernel 6.42 ms x 384 calls = 2.47 s (32 %), the three backward kernels
3.49 ms x 384 = 1.34 s (17 %), everything else 3.95 s (51 %; e001's timers put the non-attention part at 3.08 s). The
kernel-level numbers are from validation windows and random v, the step from training batches, so the split is +-0.1 s.
Evaluation gains more than training because it is all forward: 16k-context ArXiv eval is 3.5x the frozen baseline.
