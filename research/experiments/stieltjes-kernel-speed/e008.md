## Hypothesis
`_pick_blocks` asks the Triton driver for the device's `max_shared_mem` on every forward call: 1.01 ms of CPU time
(micro, e007 job 8615586), 384 calls per step, 0.39 s per step if none of it overlaps GPU work, against a forward
kernel that is now 4.24 ms on trained inputs (it was 22.8 ms when this was written, so nobody looked). The answer is a
constant of the device, so caching it per device index cannot change a tile size, a kernel or a bit.
What it is worth on the step depends on whether the CPU side is ever the bottleneck, and the evidence points both ways.
For "hidden": train.py does not synchronise inside a micro-batch, the GPU has ~190 ms of work per micro-batch against
tens of ms of Python, and adding synchronisation costs 0.69 s per step (e007), which is what losing the overlap looks
like. For "not hidden": the forward Function takes 6.22 ms in the synchronised step against 4.24-4.9 ms for the kernel
on captured inputs, the Stieltjes row carries ~0.7 s per step outside its kernels that softmax does not (e006), and e007
showed that this is not the copies. I lean to "hidden" (about 2 to 1).
Second question, measurement only: is that ~0.7 s the micro-batch split? Softmax runs 16 x 16, the sparse rows 8 x 32
(`osc/run_lm.sh`, set when the sparse kernels were thought not to fit 40 GB at 16; e001 showed 30.3 GB allocated at 16 x
16 with the baseline kernel). Softmax at both splits on the same node and the trained Stieltjes step at 16 x 16 answer
it and give the final chart a same-node softmax reference. Changing the split of a training run is a protocol decision
for the user (`osc/run_lm.sh` is not this direction's to edit); this only measures it.

## Interpretation
The device query is hidden. Removing 1.07 ms of CPU time from each of 384 forward calls changes the step by +0.002 s on
average over three pairs (each within one sd of zero): the Python side of a micro-batch finishes while the GPU still has
queued work, so CPU time inside the wrapper costs nothing in train.py. The "hidden" reading (held at 2 to 1) was right,
and the 6.22 ms the forward Function shows under synchronised timers (e007) is the timers' own artefact, not a cost of
the step. Decision: **kept** (exact, gate passed bit-identical, 7 lines, and it removes most of every small forward
call: 1.20 -> 0.07 ms at N=64), but it counts as 0 % on the primary metric. **Second strike of the stop rule**
(e007 0.0 %, e008 +0.2 %): the optimisation loop ends here.
The second question has a clear answer: the ~0.7 s the Stieltjes row seemed to carry outside its kernels was mostly the
micro-batch split. 8 x 32 costs 0.26 s per step over 16 x 16 for softmax and 0.27 s for the trained Stieltjes row (16
more micro-batches, ~16 ms each; where in the micro-batch it goes was not measured). At the same split on the same node the trained
`wstieltjes_q3_d2_xs` step is below the softmax_xs step: 6.205 against 6.684 s at 8 x 32 (-7.2 %), 5.934 against 6.428 s
at 16 x 16 (-7.7 %); from scratch it is above (7.084 against 6.684 s at 8 x 32, +6.0 %). That is consistent with the
kernels: forward + backward 5.91 ms per call on trained q/k (e006) against 7.31 ms for SDPA softmax with the NAPE bias
at the same shape. Caveat: the softmax row was timed from scratch only (a dense map, so its step should not depend on
the weights; not measured), and "softmax" here is SDPA with an additive float bias, the project's softmax_xs row.
For the user (not acted on, `osc/run_lm.sh` is outside this direction): the sparse rows fit 40 GB at mb 16 x 16 with
this kernel (30.7 GB allocated, 36.6 GB reserved for `wstieltjes_q3_d2_xs`; the AS row is 0.85 GB larger at 8 x 32 and
has not been run at 16 x 16) and gain 4.4 % from it. Changing the split changes the batches a run sees, so it is a
protocol decision.
