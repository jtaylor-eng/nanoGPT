## Hypothesis
`_pick_blocks` asks the Triton driver for the device's `max_shared_mem` on every forward call: 1.01 ms of CPU time
(micro, e007 job 8615586), 384 calls per step, 0.39 s per step if none of it overlaps GPU work, against a forward
kernel that is now 4.24 ms on trained inputs (it was 22.8 ms when this was written, so nobody looked). The answer is a
constant of the device, so caching it per device index cannot change a tile size, a kernel or a bit.
What it is worth on the step depends on whether the CPU side is ever the bottleneck, and the evidence points both ways.
For "hidden": train.py does not synchronise inside a micro-batch, the GPU has ~190 ms of work per micro-batch against
tens of ms of Python, and adding synchronisation costs 0.69 s per step (e007), which is what losing the overlap looks
like. For "not hidden": the forward Function takes 6.22 ms in the synchronised step against 4.24-4.9 ms for the kernel
on captured inputs, the Stieltjes row carries ~0.7 s per step outside its kernels that softmax does not (e006), and e007
showed that this is not the copies. I lean to "hidden" (about 2 to 1).
Second question, measurement only: is that ~0.7 s the micro-batch split? Softmax runs 16 x 16, the sparse rows 8 x 32
(`osc/run_lm.sh`, set when the sparse kernels were thought not to fit 40 GB at 16; e001 showed 30.3 GB allocated at 16 x
16 with the baseline kernel). Softmax at both splits on the same node and the trained Stieltjes step at 16 x 16 answer
it and give the final chart a same-node softmax reference. Changing the split of a training run is a protocol decision
for the user (`osc/run_lm.sh` is not this direction's to edit); this only measures it.
